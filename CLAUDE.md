# Nutrikal ERP + CRM — instructions for Claude Code

Read this before every task. README.md has run/test commands and the full rule list.

## What this is
One app (app.nutrikal.com) that runs Nutrikal's **contract manufacturing / private label** business: CRM, offers, formulation, inventory, production, QC and invoicing. Own brands (CollagenLab, GutExpert) are OUT of scope — they move to a separate company and separate software later.

Production is outsourced to ONE partner facility but run as if in-house. The facility has one user in this app with the restricted role `production`.

Talk to the owner in the language they write in (usually Bulgarian).

## Decisions already made (do not reopen without asking)
- ERP and CRM are ONE system on ONE database; clients, projects, stock, batches and invoices link to each other.
- Nutrikal owns all raw materials, packaging and finished goods at every location.
- Partner invoices Nutrikal per batch (record against the batch for actual cost).
- Client-supplied materials: not in v1.
- Offers are costed per unit and priced by product format.
- Deleting a client (owner, Nov 2026): Admin any client, Sales and the bookkeeper only the clients they are responsible for (`owner_id`), through `delete_client`; refused while the client has offers, orders, recipes, projects, own items or invoices; its contacts, notes, files, portal access and the mail saved from Gmail go with it (the mail stays in Gmail); catalogue enquiries stay, unlinked.
- Payment terms: by default 60% deposit + 40% before dispatch (owner, Nov 2026); editable per order; the client form has no payment-term fields (owner, Nov 2026), so new clients follow the company default. Nor a document language: every download of a document (offer, proforma, invoice, credit and debit note, delivery note, purchase order; also in the customer panel) first asks Download in BG / Download in EN (`DocLangDialog`, `ProformaPdfButton` takes both versions; owner, Nov 2026). The page preview and the e-mail keep the stored `preferred_locale` (a new client: bg for Bulgaria, else en; e-mailed offers stay in English). A document in Bulgarian names the company with its Bulgarian name and address and the offer with Bulgarian terms (`company_name_bg`, `company_address_bg`, `terms_text_bg` under Settings; `company_bg()` for every account, the customer panel too; owner, Nov 2026).
- The ERP issues FINAL invoices. Invoice numbers: one 10-digit series shared by invoices, credit and debit notes; editable on a draft before issue with duplicate/gap warnings and audit log. An issued invoice or note is corrected in full by Admin at any time (owner, Nov 2026, against the advice that VAT Act art. 116 allows corrections only by notes): number, dates, terms, VAT, language, notes, buyer and lines through `correct_invoice`, with a required reason; the invoice as it was is kept in `invoice_versions` and the page shows Corrected on … by …; everyone else still cannot change an issued one, and credit/debit notes stay. Design the invoice data to map to EN 16931 (Bulgaria plans mandatory structured e-invoicing from 2028).
- Shelf life is tracked per raw material. Recipes have none (owner, Oct 2026): the expiry date of a finished batch is entered when it is reported.
- Materials are released on receipt; finished batches need Admin release before dispatch; the COA is optional and can be attached later. Any lot can be blocked (owner, Oct 2026). Under Stock, Admin picks an item and adds or changes the expiry date and the supplier's batch number of each of its lots; both optional, an empty field clears it (`set_lot_details`, audited; owner, Nov 2026).
- No minimum stock (owner, Nov 2026): items have no minimum or reorder level; nothing warns that stock is low (stock page, dashboards, purchasing, AI). Missing materials come only from purchase requests of orders. Do not add it back without asking.

The old sub-stores PF-QUAR, PF-RM, PF-PACK are inactive; their stock was moved through the ledger. ## Architecture rules
- **All data access runs as the signed-in user** through `withUser()` / `q()` in `web/src/lib/db/engine.ts`. Row-level security and role checks live in the database (`supabase/migrations`). Never bypass them and never duplicate permission logic in the UI beyond hiding buttons.
- **Stock is a ledger** (`stock_movements`): never update stock numbers; write through the SQL functions (`receive_lot`, `transfer_stock`, `post_stock_movement`, `reserve_stock`, …).
- **Production must never see** client names, sales prices, offers, delivery notes or Nutrikal's invoices. Projects appear to them by code only (`production_projects`). Exception decided by the owner (Oct 2026): supplier, ordered quantity, purchase price and date of the materials of their own orders (`mo_material_sources`, read only), and the supplier of deliveries to their locations. Any new table or view needs an explicit RLS decision for the production role, and a test.
- **Schema changes** = a NEW migration file in `supabase/migrations` (timestamped name). Once a migration has been applied to Supabase, never edit it.
- With the Supabase values in `web/.env.local` the app uses Supabase (database via `DATABASE_URL`, Auth email + password, Storage); new migrations go there with `cd web && npm run db:migrate`. Users are created in Supabase Auth + a `profiles` row (README). Without those values (development) the database is PGlite in `web/.data/` (created from the migrations + `web/src/lib/db/demo-seed.ts`). New migrations are added to the kept local database on start (`nk_local.migrations`), so local data survives updates; delete `web/.data/` only after changing an applied migration or the seed.
- Next.js 16 with `cacheComponents: false` (every page is per-user and dynamic). Read `web/node_modules/next/dist/docs/` before using unfamiliar Next.js APIs — this version differs from older ones.

## Documents
Offer, proforma, invoice, credit and debit notes, purchase order and delivery note share one look (owner, Nov 2026): dark top with the wordmark and a bold title, capsule photo `web/public/doc-bg.jpg`, white sheet (`drawDocShell` in `lib/calculator/pdf.ts`, `.doc-brand` on screen), contacts under the logo and a strip at the foot with the page number (`lib/doc-chrome.ts`); invoices and notes end with the lines to sign. Offers follow the owner's mock: Prepared for and by, a product row (product, pack, format), the composition as one list (one column up to 10 ingredients, two above), prices as cards set apart lower on the page, what is included and what is not, short small print, payment terms at the foot of the last page (owner, Nov 2026).
Text layout in every generated document (owner, Nov 2026): all PDF text goes through `web/src/lib/pdf-layout.ts` (`PdfLayout` wrap/text/row, `PdfFlow`, `footStrip`, `TABLE_RULES`); every text has a column (x and width) and wraps below itself in it, whole words, a word split only when wider than its column; rows and blocks grow with the tallest cell; nothing is cut, shortened with … or set smaller to fit, so a long offer continues on a second page; a block that does not fit moves to the next page whole, tables repeat their head and never split a row. No fixed-coordinate text without a width. HTML documents (`.doc`) wrap with `overflow-wrap: anywhere`.

## UI rules
- **Every user-visible string goes in BOTH `web/src/lib/i18n/en.ts` and `bg.ts`.** No hard-coded text in components. Use `fmt()`, `formatNumber/Qty/Money/Date` from `web/src/lib/i18n`. Dates show as day/month/year, e.g. 03/11/2026, in every language (`formatDate`; owner, Nov 2026).
- **NEVER horizontal scrolling** on any page or width (owner's strong rule). Data lists use CSS grid rows (`.row`) and drop columns on narrow screens with `hide-md` (<1024px) / `hide-sm` (<768px) — no `<table>` with overflow.
- The signed-in app uses Inter at 14px with tabular numbers and sentence-case buttons and labels (`.app-ui` in globals.css, owner, Nov 2026); on wide screens rows and buttons may be under 44px. The open catalog keeps Poppins and the button style below. Right-align money and quantities in lists.
- Design tokens from nutrikal.com live in `web/src/app/globals.css`: Poppins (Montserrat for Cyrillic), ink #222831, white, light grey #EBEBEB, border #C6CDD9, green #7BC74D only for positive states, red #D72C0D for critical. Buttons: `.btn .btn-primary` / `.btn-outline` (uppercase, 12px, 600, wide tracking, 2px radius).
- Touch targets ≥ 44px; real `<button>`, `<a>`, `<label>`; text contrast ≥ 4.5:1.
- Items show `name_bg` in the Bulgarian interface when present.

## EU / regulatory context (food supplements)
Flag ingredients with Novel Food status (Reg. 2015/2283); health claims only from the EU Register under Reg. 1924/2006 at the right conditions of use; labelling per Reg. 1169/2011 and Dir. 2002/46/EC (NRV %); batch traceability per Reg. 178/2002 art. 18.

## Before you finish a task
1. `cd test && node run-tests.mjs` — database rules (must stay green; add tests for new rules).
2. `cd web && npx tsc --noEmit && npm run build`.
3. For UI changes: check the page in both languages and at phone width; no sideways scroll.
4. Commit on a branch with a clear message; open a Pull Request for the owner to review.
