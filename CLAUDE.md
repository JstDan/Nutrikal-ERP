# Nutrikal ERP + CRM — instructions for Claude Code

Read this before every task. README.md has run/test commands and the full rule list.

## What this is
One app (app.nutrikal.com) that runs Nutrikal's **contract manufacturing / private label** business: CRM, offers, formulation, inventory, production, QC and invoicing. Own brands (CollagenLab, GutExpert) are OUT of scope — they move to a separate company and separate software later.

Production is outsourced to ONE partner facility but run as if in-house. The facility has one user in this app with the restricted role `production`.

Talk to the owner in the language they write in (usually Bulgarian).

## Decisions already made (do not reopen without asking)
- ERP and CRM are ONE system on ONE database; clients, projects, stock, batches and invoices link to each other.
- Nutrikal owns all raw materials, packaging and finished goods at every location.
- Partner invoices Nutrikal per batch (record against the batch for actual cost).
- Client-supplied materials: not in v1.
- Offers are costed per unit and priced by product format.
- Payment terms: by default 60% deposit + 40% before dispatch (owner, Nov 2026); editable per client and per order.
- The ERP issues FINAL invoices. Invoice numbers: one 10-digit series shared by invoices, credit and debit notes; editable on a draft before issue with duplicate/gap warnings and audit log; locked after issue; corrections only via credit/debit notes. Design the invoice data to map to EN 16931 (Bulgaria plans mandatory structured e-invoicing from 2028).
- Shelf life is tracked per raw material. Recipes have none (owner, Oct 2026): the expiry date of a finished batch is entered when it is reported.
- Materials are released on receipt; finished batches need Admin release before dispatch; the COA is optional and can be attached later. Any lot can be blocked (owner, Oct 2026).
- Documents are e-mailed through the Resend HTTP API (the host, Cloudflare Workers, has no SMTP); every send is logged in `document_sends` (owner, Oct 2026).
- New offers are made only in the calculator; older ERP offers stay readable and usable but cannot be created. Production of an order is planned with Prepare production (owner, Oct 2026).
- Offer to production, end to end (owner, Nov 2026; the chain is tested in `test/run-tests.mjs` "End to end"): a recipe from a catalog offer follows the catalog product (format, capsules per serving, servings = capsules per jar on the offer ÷ capsules per serving, composition, capsule, jar and lid), never fields of a custom formula left in the form; an offer in an order is never overwritten (the form becomes a new offer); an order from calculator offers takes the client's payment terms, else the company default; the bookkeeper confirms payments; a recipe without servings per pack is named by Prepare production and fixed on the recipe page; materials in the Nutrikal warehouse are moved to the partner with Move to production on the batch; a ready, paid order is invoiced before it is dispatched. A downloaded proforma (advance or final) is kept as a file on the order tasks, Payments & invoices: the advance one on Payment, the final one on Proforma for the final payment; one downloaded before the board exists waits in `order_proforma_pending` and moves there when the first payment is confirmed; the latest copy replaces the earlier (owner, Nov 2026).
- AI: OpenAI API directly, not Kie.ai (owner, Oct 2026): Responses API with `store: false` (AI_BASE_URL, AI_API_KEY, AI_MODELS; `web/src/lib/ai/gateway.ts`). The assistant only reads, through fixed queries run as the signed-in user (`web/src/lib/ai/tools.ts`); AI proposes and a person approves: recipes proposed in the chat become drafts only when a person saves them; figures come from `recipe_estimate`, never from the model; purchase prices follow `can_see_purchase_prices`. Health claims and Novel Food status come from `eu_health_claims` and `eu_novel_food_status` (public EU lists, refreshed with `web/scripts/eu-lists.mjs` into a new migration). There are no harmonised EU maximum doses. Production has no AI access (owner, Oct 2026).
- Gmail: one shared mailbox connected once by Admin with `gmail.readonly` (owner, Oct 2026). Gmail is searched only for client addresses (domains, full addresses on public mail services); a changed list starts over from 12 months back. Only mail to and from known clients is kept (`client_emails`); Production has no access; the token is encrypted (`gmail_connection`, no policies). Mail reaches the AI only with AI_READ_MAIL=on; the data processing agreement with OpenAI is signed (owner, Oct 2026). Mail is shown only through the AI assistant, not on client pages or the dashboard (owner, Nov 2026). The assistant also searches the whole shared mailbox live with Gmail search (`search_gmail`: labels, unread, any sender; nothing saved; Admin and Sales; at most 2 searches an answer because of the Workers request limit; owner, Nov 2026).
- Invoices can be issued without an order, directly to a client, with free lines, due date, way of payment and recorded payments (`invoice_payments`, Admin writes); same number series; issued invoices stay locked. A proforma is made from such a draft on its own series (PF-); 0 % VAT needs a printed basis; invoices of orders count as paid from the order; copying an invoice and payment reminders are by hand only (owner, Oct 2026).
- Production contract (planned, not built; owner, Oct 2026): optional per order, sent with the proforma, never blocks an order. The owner provides the template later. Planned: client accepts through a link (time, address, PDF copy kept) or Admin marks it signed by hand.
- Chat is in the side menu (/chat, the full view) and in the header (`chat-drawer.tsx`, a panel over any page) (owner, Oct 2026): channels, direct messages, files, mentions, reactions, Nutrikal emoji (`web/public/emoji`). Production sees only channels of kind external, no direct messages. Admin creates channels; new messages come by polling, not realtime (owner, Oct 2026). The accountant writes in it through `qChat` (no read-only transaction): has_role() is false there, so only the chat rules apply; never use qChat for anything else. Client files (`client_files`, bucket client-files, up to 24 MB) sit on a client and optionally an order.
- All settings live under Settings and are Admin only (owner, Oct 2026). New settings go there.
- Catalogue of stock formulas (owner, Oct 2026): any recipe, also one of a client, can become a product (`catalog_products`) and be published; Admin manages it, Sales reads it and handles enquiries. Prices by quantity tiers; the minimum order is per product (500 packs by default, protein bars 3000). A product can stand alone with its composition as text until a recipe is tied to it; the products of the owner's PDF and price list are published by the owner's decision (Oct 2026). catalog.nutrikal.com is the same app: the middleware sends that address only to /public-catalog, open to everyone, with a quote list (opens when a product is added) and one enquiry, plus a contact form. New formulations (NEW-xxx) were published by the owner (Nov 2026) as price on request, with open reviews recorded in their internal notes. Internal notes, sources and specifications never reach the public side; a set `review_status` blocks publishing. A product can sit in several categories (`catalog_product_categories`). The public ingredient list is `catalog_ingredient_list`: cleaned names kept apart from `items`, so stock, suppliers and prices stay private; edited under Catalog. Capsule colors: clear, black, green. Nutri AI on the open catalog (`catalog-sales.ts`, /api/catalog-chat) sees only `catalog_public()`, never the database or customers, and writes only enquiries through `catalog_submit_enquiry()`, makes no health claims and promises no prices. It always leads with stock formulas: custom work is not always possible and branded raw materials can raise minimums and prices, so it promises none. It shows products as cards built from the catalog data ([[CODE]] in its answer), never from the model. The chat is a centred window opened from a button at the bottom right; WhatsApp is a line at the top of the chat ("a real person during working hours") and under Contact; a visitor who asks for a person is referred there at once. The country of a quote follows the language and stays editable. The visitor's device keeps the conversation for 30 days; the model gets the last 40 messages. Limits: 100 questions a chat, 40 a visitor a day, 500 a day; AI_CATALOG_MODEL picks the model, default the last in AI_MODELS. Conversations are read under Catalog > Conversations; those without an enquiry go after 12 months. The page carries the company story in the style of the presentation, the video under About us (YouTube loads only on play), certificates and presentation; files in `web/public/catalog/site`. The open page runs as anon (`qPublic`) and reaches only `catalog_public()` and `catalog_submit_enquiry()`. Categories follow the owner's catalogue. Health claims on the page come only from the approved recipe.
- Customer panel (owner, Nov 2026): portal.nutrikal.com is the same app; the middleware keeps that address on /portal (PORTAL_HOST). A client account (role client, `client_users`, made by Admin on the client page) has no rights on any table and reads only through the `portal_` functions, limited to its client and to chosen columns; `getSession()` sends it away from every staff page. A new table, view or rule written as "any account" must keep clients out; the test over all tables checks it.
- Production calendar (owner, Nov 2026): /production/calendar for the team, /factory/calendar for the partner. Admin moves batches by dragging; every new date goes back to the partner, who confirms it or proposes another, and Admin decides a proposal. - Reasons for material above plan are chosen from fixed codes (scrap, spill, setup, sample, weight in `mo_material_usage.reason`) or written under Other; Scrap and losses, a tab of Quality (Admin, `mo_loss_report`), counts them by reason and product (owner, Nov 2026).

## Architecture rules
- **All data access runs as the signed-in user** through `withUser()` / `q()` in `web/src/lib/db/engine.ts`. Row-level security and role checks live in the database (`supabase/migrations`). Never bypass them and never duplicate permission logic in the UI beyond hiding buttons.
- **Stock is a ledger** (`stock_movements`): never update stock numbers; write through the SQL functions (`receive_lot`, `transfer_stock`, `post_stock_movement`, `reserve_stock`, …).
- **Production must never see** client names, sales prices, offers, delivery notes or Nutrikal's invoices. Projects appear to them by code only (`production_projects`). Exception decided by the owner (Oct 2026): supplier, ordered quantity, purchase price and date of the materials of their own orders (`mo_material_sources`, read only), and the supplier of deliveries to their locations. Any new table or view needs an explicit RLS decision for the production role, and a test.
- **Schema changes** = a NEW migration file in `supabase/migrations` (timestamped name). Once a migration has been applied to Supabase, never edit it.
- With the Supabase values in `web/.env.local` the app uses Supabase (database via `DATABASE_URL`, Auth email + password, Storage); new migrations go there with `cd web && npm run db:migrate`. Users are created in Supabase Auth + a `profiles` row (README). Without those values (development) the database is PGlite in `web/.data/` (created from the migrations + `web/src/lib/db/demo-seed.ts`). Delete `web/.data/` after changing migrations or the seed.
- Next.js 16 with `cacheComponents: false` (every page is per-user and dynamic). Read `web/node_modules/next/dist/docs/` before using unfamiliar Next.js APIs — this version differs from older ones.

## Documents
Offer, proforma, invoice, credit and debit notes, purchase order and delivery note share one look (owner, Nov 2026): dark top with the wordmark and a bold title, capsule photo `web/public/doc-bg.jpg`, white sheet (`drawDocShell` in `lib/calculator/pdf.ts`, `.doc-brand` on screen), contacts under the logo and a strip at the foot with the page number (`lib/doc-chrome.ts`); invoices and notes end with the lines to sign. Offers follow the owner's mock: Prepared for and by, a product row (product, pack, format), the composition as one list (three columns from 7 ingredients), prices as cards set apart lower on the page, what is included and what is not, short small print, payment terms at the foot; always one page: the body shrinks until it fits (owner, Nov 2026).

## UI rules
- **Every user-visible string goes in BOTH `web/src/lib/i18n/en.ts` and `bg.ts`.** No hard-coded text in components. Use `fmt()`, `formatNumber/Qty/Money/Date` from `web/src/lib/i18n`. Dates show as day/month/year, e.g. 03/11/2026, in every language (`formatDate`; owner, Nov 2026).
- **NEVER horizontal scrolling** on any page or width (owner's strong rule). Data lists use CSS grid rows (`.row`) and drop columns on narrow screens with `hide-md` (<1024px) / `hide-sm` (<768px) — no `<table>` with overflow.
- The signed-in app uses Inter at 14px with tabular numbers and sentence-case buttons and labels (`.app-ui` in globals.css, owner, Nov 2026); on wide screens rows and buttons may be under 44px. The open catalog keeps Poppins and the button style below. Right-align money and quantities in lists.
- Design tokens from nutrikal.com live in `web/src/app/globals.css`: Poppins (Montserrat for Cyrillic), ink #222831, white, light grey #EBEBEB, border #C6CDD9, green #7BC74D only for positive states, red #D72C0D for critical. Buttons: `.btn .btn-primary` / `.btn-outline` (uppercase, 12px, 600, wide tracking, 2px radius).
- Touch targets ≥ 44px; real `<button>`, `<a>`, `<label>`; text contrast ≥ 4.5:1.
- Items show `name_bg` in the Bulgarian interface when present.

## EU / regulatory context (food supplements)
Flag ingredients with Novel Food status (Reg. 2015/2283); health claims only from the EU Register under Reg. 1924/2006 at the right conditions of use; labelling per Reg. 1169/2011 and Dir. 2002/46/EC (NRV %); batch traceability per Reg. 178/2002 art. 18.

## Before you finish a task
1. `cd test && node run-tests.mjs` — database rules (must stay green; add tests for new rules).
2. `cd web && npx tsc --noEmit && npm run build`.
3. For UI changes: check the page in both languages and at phone width; no sideways scroll.
4. Commit on a branch with a clear message; open a Pull Request for the owner to review.
